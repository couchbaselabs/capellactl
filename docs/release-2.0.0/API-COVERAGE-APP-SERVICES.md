## Dependencies on 1.0.0

- An App Service is created **under a provisioned cluster** (`POST …/clusters/{c}/appservices`), so it builds on the 1.0.0 cluster, bucket, scope and collection reconcilers. App Endpoints bind to a bucket's scopes and collections, which needs [CAP-025](../release-1.0.0/CAP-025-ensure-scopes-collections.md).
- `POST …/clusters/{c}/activationState` (1.0.0 `cluster power on`, [CAP-019](../release-1.0.0/CAP-019-power-cluster-off-on.md)) already accepts `turnOnLinkedAppService`. In 1.0.0 it is always `false`; 2.0.0 should expose it.
- Deleting a cluster that has a linked App Service needs an ordering rule in the 1.0.0 dependency graph ([00-architecture.md](../release-1.0.0/00-architecture.md) §4.2): delete the App Service first.
- The patterns for allowed CIDRs, audit-log export, private endpoints and power on/off mirror the cluster-level 1.0.0 work, so their reconcilers and tests can be reused.
